# 阶段 0 — 技术验证报告

> 目的：在投入功能开发前，验证「Rust 核心 + Qt/QML（cxx-qt 桥接）」技术栈可行性，并实测冷启动性能以敲定 MVP 门槛。
> 结论日期：2026-10-17。所有数据均为本机实测（Windows 10/11 x64，非管理员权限）。

## 1. 结论摘要

1. **技术栈可行**：Cargo workspace + 纯 Rust 解码/渲染/编辑模型 + cxx-qt 0.10 桥接 + Qt 6.8.3 QML 界面，全链路已跑通（`cargo test --workspace` 19 项通过；UI 自测 `--selftest` 退出码 0）。
2. **冷启动门槛需修订**：原 v0.5 分级门槛（小图 < 300ms / 中图 < 600ms / 大图 < 1.2s）**实测不可达**，主因是 **Qt/QML 固定开销 ~290–425ms**（窗口显示 + RHI 初始化 + 首帧），与图片尺寸无关。
   - **已修订为（v0.6）**：所有尺寸 **≤ 2000ms**（上界），**目标 ≤ 1000ms**。实测 D3D11 默认路径：小图 503ms、中图 699ms、大图 1246ms，**全部达标**。
3. **渲染后端默认 D3D11**（Qt 默认）。本机软件渲染器更快，但那是虚拟显示适配器环境导致的假象（见 §5.3），实机 GPU 路径对后续全分辨率缩放/平移更有利。
4. **便携版打包验证通过**：`windeployqt` 产出的目录在无任何 Qt 环境变量的情况下可独立运行（57.4MB，可裁剪至约 35MB）。
5. **主要技术债**：预览图当前经「临时 PNG 写盘 → Qt 读回解码 → 上传纹理」通道传递，应改为 `QQuickImageProvider` 直传（这是下一阶段首要优化项）。

## 4. 验证结果

### 4.1 纯 Rust 层

- `cargo test --workspace`：**19 项通过**（core 7 / decode 8 / render 4）。
- 覆盖：格式探测与解码（JPEG/PNG/GIF/BMP/TIFF/WebP）、编码回写、像素上限保护、选区提取与图层跨文档复制粘贴、撤销/重做（含旧值回滚）、视口缩放与裁剪、文档合成。
- 冷启动基准（release，Rust 自身派生计时，p50）：

| 场景 | 耗时 |
| --- | --- |
| 仅进程启动（无解码） | 34.4ms（min 32.7） |
| 小图 1.9MP jpg / png | 59.7 / 52.9ms |
| 中图 12MP jpg / png | 177.6 / 142.2ms |
| 大图 50MP jpg / png / webp / bmp / tiff | 633.0 / 516.9 / 442.3 / 249.6 / 206.5ms |

样本为高熵合成图（最坏情况）。结论：**Rust 侧余量充足**；50MP JPEG 全量解码 633ms 是最大单项，验证了「大图需降采样优先解码」（libjpeg-turbo scaled decode / 渐进解码）为必要设计要点。

### 4.2 cxx-qt 桥接

- 采用官方书中的 **pure-Cargo 方案**（无需 Corrosion），只需 `qmake` 在 PATH 可见。
- 构建链路：`build.rs` 用 `CxxQtBuilder::new_qml_module(QmlModule::new("com.imageedit").qml_file("qml/main.qml"))` 生成 C++ 桥接、moc、qmltyperegistrar、qmlcachegen 与 QML 资源；`main.rs` 加载 `qrc:/qt/qml/com/imageedit/qml/main.qml`。
- 已验证：QObject 属性双向绑定、`#[qinvokable]` 从 QML 调用回 Rust、QML 类型注册（`import com.imageedit` 后 `Bridge` 解析为 `imageedit::Bridge`）。

### 4.3 冷启动端到端实测（核心）

测量方式：`imageedit-bench ui <file> --repeat N` —— 用 Rust 建立子进程并打时间戳，取「**进程 spawn → 首帧含图渲染完成**」（子进程在 QML `afterRendering` 中回报 `image-frame`），避免 PowerShell `Start-Process` 的约 1s 固定开销。

| 图片 | D3D11 p50 | 软件渲染器 p50 | OpenGL p50 | 门槛 |
| --- | --- | --- | --- | --- |
| tiny 64×64 | 426ms | 291ms | – | – |
| small 1.9MP jpg | **503ms** | 382ms | 662ms | ≤2000 ✓ |
| medium 12MP jpg | **699ms** | 550ms | – | ≤2000 ✓ |
| large 50MP jpg | **1246ms** | 1103ms | 1404ms | ≤2000 ✓ |

**固定开销拆分**（D3D11，in-main 计时，小图）：

| 阶段 | 累计耗时 |
| --- | --- |
| 进程启动 → `main`（exe + Qt DLL 加载） | ~48ms |
| `QGuiApplication` 构造完成 | ~24ms |
| `QQmlApplicationEngine` 构造完成 | ~27ms |
| 窗口创建并可见（`engine.load()` 内） | ~81ms |
| QML 组件实例化完成（`Component.onCompleted`） | ~366ms |
| 首帧渲染完成 | ~465ms |

关键对照实验：

- **不显示窗口**（`--hidden`）：`engine.load()` 返回仅 **102–105ms** ⇒ 约 290ms 全部花在「窗口显示 + RHI 初始化 + 首帧」。
- `QSG_RENDER_TIMING=1`：GUI 线程 `blockedForSync=167ms`（等待渲染线程首次 sync），渲染线程 `syncAndRender` 首帧间隔 150ms；而 pipeline 创建总耗时 `0 ms`（非着色器编译问题）。
- `QSG_INFO=1`：D3D11 后端，枚举 5 个适配器并选用 RTX 4090。

⇒ **门槛未达成的唯一原因是 Qt 工具链固定开销，不是我们的解码/渲染逻辑**。

### 4.4 便携版打包

- `windeployqt --release --no-translations --qmldir crates/ui/qml` 产出 **57.4MB**。
- 体积构成：`opengl32sw.dll` 19.7MB、`Qt6Gui` 8.9MB、`Qt6Quick` 6.0MB、`Qt6Core` 5.9MB、`Qt6Qml` 5.0MB、`imageedit.exe` 2.0MB，其余为插件与 QML 模块。
- **独立运行验证通过**：清空 PATH 中的 Qt 路径后运行打包版，退出码 0、各阶段打点完整；暖态首帧 437–464ms，与开发态一致。

## 5. 关键技术发现与坑

### 5.1 cxx-qt 0.10

- **QML 属性/方法名不做 camelCase 转换**：`#[qproperty(QString, preview_url)]` 在 QML 中必须写 `bridge.preview_url`，`#[qinvokable] fn image_shown` 必须写 `bridge.image_shown()`（官方示例里的驼峰来自显式 `#[cxx_name]`）。这是最容易踩的坑：写错报 `Unable to assign [undefined]`。
- 桥接声明中**不允许 `mut self`**，必须 `self: Pin<&mut Self>`；impl 块中才写 `mut self: Pin<&mut Self>`。
- `on_object_creation_failed` 的闭包签名带发送者，需 `|_, _|`。
- **`QCoreApplication` 无 `quit()` 绑定**（0.10）：退出只能走 QML `Qt.quit()`。
- `ApplicationWindow` 属 QtQuick.Controls，若未部署 Controls 会报 `ApplicationWindow is not a type`；本项目用 `Window`（`QtQuick.Window`），零额外依赖。
- cxx-qt-lib 0.10 提供 `QQmlImageProviderBase`，可支撑后续 `QQuickImageProvider` 直传。

### 5.2 Qt / 平台行为

- **`Image` 默认同步加载本地文件**（`asynchronous: false`）：`set_preview_url()` 会在 QML 内**同步**触发 `onStatusChanged` → 重入 Rust 的 `#[qinvokable]`。因此必须**先把所有标量属性赋好，最后再赋值 `preview_url`**，否则读回默认值。
- **Qt 在 Windows 上把日志送到 OutputDebugString**（当 stderr 不是控制台时），导致 QML 错误「无声」——排查时需设 `QT_ASSUME_STDERR_HAS_CONSOLE=1`。这是定位 `qml-load-failed` 的关键。
- QML 资源路径由 `QmlModule` URI 决定：`qrc:/qt/qml/<uri 以 / 分隔>/<qml 文件相对路径>`，本项目中即 `qrc:/qt/qml/com/imageedit/qml/main.qml`。

### 5.3 环境相关（影响数据解读）

- 本机图形栈为**虚拟显示适配器**（`GameViewer Virtual Display Adapter` + `OrayIddDriver Device`，另有 RTX 4090 / Intel UHD 770 / Microsoft Basic Render Driver 共 5 个 D3D 适配器）。会话为 Console 但输出经 IDD 回传。
- 因此 **D3D11 的窗口 + swapchain + 首帧成本可能被显著抬高**，软件渲染器反而更快（省 ~120ms，且预览已在 Rust 侧降采样至 ≤1600px，软件光栅化负载极低）。
- **建议**：在带物理显示器的机器上重跑 `imageedit-bench ui`，用真实底噪复核 §4.3 的固定开销。

### 5.4 构建环境

- 用户级环境变量 `CC`/`CXX` 指向 LLVM clang，会使 cxx 生成代码编译失败（`-std=c++11` 与新版 MSVC 头不兼容）。**不修改用户环境**，改由 `scripts/env.ps1` 在会话内清除（含 `CC_x86_64_pc_windows_msvc` / `CXX_x86_64_pc_windows_msvc`）。
- PowerShell 5.1：`Start-Process -Wait` 存在约 1s 固定开销（对照 `cmd /c exit` 仅 37.9ms），**计时必须用 Rust 派生进程**；`$ErrorActionPreference='Stop'` 会把 cargo 的首条 stderr 变成终止错误，已从脚本移除。

## 7. 待改进项（技术债）

1. **预览通道**：当前为「Rust 编码 PNG → 写临时文件 → Qt 读文件解码 → 上传纹理」，多一次编码+解码+磁盘往返。应改为 `QQuickImageProvider`（或 `QQmlImageProviderBase`）直接交付 `QImage`/纹理所指数据。
2. **大图解码**：50MP 全量解码 769ms（UI 内实测），需引入降采样优先解码（libjpeg-turbo scaled decode）与逐行渐进显示。
3. **打包裁剪**：排除 `opengl32sw.dll`(19.7MB)、`qmltooling`(1MB) 及未用 QML 模块，预计可降至约 35MB；并提供可复现的打包脚本。
4. **诊断开关**：`--hidden` 目前借 `Qt.application.arguments` 在 QML 内判断，属临时诊断手段。
5. **退出路径**：cxx-qt 0.10 无 `QCoreApplication::quit` 绑定，退出完全依赖 QML 侧 `Qt.quit()`；多窗口/错误路径需要专门设计。
6. **UI 层格式覆盖**：`crates/decode` 已支持 6 种格式，但 UI 目前只走了 JPEG/PNG 预览通道。
7. **可视化确认**：尚无截图/人工目视验证（自测仅以打点退出码判定），阶段 1 需补。
